# 同步与性能修复：1.8.0 验证阶段，合入 1.8.1 发布

基于已发布 1.7.0 的后续修复，仍保留 React/Vite、aiohttp、SQLite、用户 JSON、资源 ID 与文件事务。此文记录 1.8.0 候选源码的测量与行为，该批改进随 1.8.1 一并发布；历史测量不因版本整理而重标为 1.8.1 重新采样，也不等同于用户安装环境的部署后验收。

## 排查结论

- 实际安装版本为 1.7.0，检查时已有 14,317 条在线索引。近期刷新任务从入队到完成约 6–20 秒；历史记录中还存在数分钟等待。这包含排队时间，不能作为单独的扫描耗时。
- 增量刷新仍重复遍历目录并两次核对全库身份。当前改为一次目录遍历，同时记录图片和空目录；提交只处理变化的身份，复用已读取的纳秒 mtime。无变化不改写目录库，目录局部更新不删除其他范围快照。
- 颜色分析记录中有 348 次像素类型错误。修正新版 Pillow 返回 RGBA 元组时的解析；尺寸完整时不再建立空任务。同种分析只运行一项，额外变化合并为一项后续任务。
- 刷新等待与全局状态中心原本分别读取任务状态；设置和错误路径还会建立额外提示。现在共用一个监听器，以真实 job ID 关联记录，不再根据相同任务类型猜测归属。
- 真实 ComfyUI 的 API 工作流完成事件可能只发给该 API 客户端；普通网页和 BroadcastChannel 都收不到。新后端从注入的 ComfyUI 完成历史读取紧凑的输出范围，不读取工作流模型参数，也不包裹或修改宿主方法。

## 同步和反馈

工作流完成历史、HTTP 桥接和浏览器广播按 prompt ID 去重。可见且启用自动同步的图库每秒读取轻量通知，合并一秒内的输出范围后提交一个公共父范围刷新。通知检查不遍历磁盘、不创建任务；初次历史只建基线。关闭同步或隐藏页面后暂停检查；外部文件和旧宿主仍保留 15 秒 freshness 兜底。

明确的完成通知不再先排一次 freshness 扫描。索引成功后并行读取页面与目录；相同快照复用原卡片和数组，不重建瀑布流。只有最新页、靠近顶部且没有选择/拖动/详情时自动替换；其他位置保留浏览状态。用户在请求期间新建的选择也受保护。元数据回填本身不显示“有新图片”。

首次校准覆盖所有已注册来源，避免首次打开旧文件夹时遗漏其他目录的旧完成记录。后续已知输出才缩小到对应范围。任务记录内部的输出进程标识和序号；比新输出更早启动的扫描不能替它确认成功，尚未执行的覆盖任务则可吸收最新序号。前端也会使较早的共享等待失效，保留必要的后续同步。

前端采样发现目录排序是插入新图时的主线程热点。当前复用一个自然排序器，每次排序只解析一次各目录的 Pin、日期和修改时间；只计算正在使用的树形或列表视图。未变化的目录、图版和移动目标保留对象引用。派生全文索引另用 `gallery_fts_rows` 保存路径到 FTS rowid 的映射，避免每个变化图片都按未索引的路径字段全表删除；全文重建时同时清空映射。

状态中心与刷新等待共用任务观察器。新服务通过变化版本唤醒异步等待，旧服务降级为每两秒查询；取消订阅不取消服务端工作，隐藏页面中断 HTTP，失败退避。浮层仍最多三条，后台维护延迟两秒显示，失败保留。新的任务不继承上一任务已经隐藏的状态或旧的等待时间。

## 兼容接口

| 接口 | 行为与限制 |
| --- | --- |
| `GET /universal_gallery/api/sync-status?since=N` | 只读通知快照，返回进程 instance、sequence 和事件；非负安全整数，最多保留 256 个 prompt，不写用户状态，不扫描文件 |
| `POST /universal_gallery/api/sync-notifications` | 同源 JSON：`version:1`、1–200 字符 `prompt_id`、最多 128 条 `outputs`；只消费 output/input/temp 的相对 subfolder，验证注册来源和路径边界，最多 32 个范围 |
| `GET /universal_gallery/api/jobs` | 原字段保留，新增 `revision`；可传 `after` 和 `wait_ms`（0–20000），最多 32 个异步等待者，不占查询线程 |

只公开原有 `refresh_index` / `fingerprint_assets` 任务类型。新增通知不接收函数、命令或任意磁盘路径。来源离线、目录库故障和文件事务恢复门禁仍有效。目录库身份与用户 JSON 不迁移；派生索引通过现有迁移机制增加纳秒时间缓存。

## 验证方式和边界

运行 `scripts/verify.ps1`，并单独运行固定版本 LoRA Manager 集成。新增用例覆盖单次扫描/变化身份计数、同秒编辑、父范围合并、源权限、完成历史去重、无网页 API 工作流、共享任务监听、异步等待取消、陈旧 POST 响应和提示生命周期。

扫描优化阶段使用 `scripts/compare_refresh.py --baseline-root <1.7源码> --source <隔离PNG目录> --output artifacts/comparison.json`，在同一个只读物理目录上交替 A/B、B/A 运行，两边使用不同临时目录库。14,317 张生成 PNG，5 次预热、30 次采样，P95 使用 nearest-rank。旧基线为 `d83cba9`。此记录测量单次扫描和身份增量改造，早于之后的 FTS rowid、无用 URL 构造移除和前端排序改造；不是最终源码逐项重新采样的结果。

| 操作 | 1.7 P50 / P95 | 扫描优化阶段 P50 / P95 |
| --- | --- | --- |
| 全库刷新 | 2508 / 4275ms | 932 / 1876ms |
| 50 张图片的局部目录刷新 | 1370 / 3982ms | 70 / 241ms |
| 热列表查询 | 42 / 50ms | 42 / 49ms |
| 热上下文查询 | 122 / 138ms | 122 / 141ms |

全库无变化时，身份登记从每次 28,634 项降为 0，目录访问从 578 降为 289；局部目录从 290 降为 1。两个普通查询的 P95 均在基线 120% 内。独立树的早期比较受 Windows 文件创建及并发负载影响，保留原始日志但不用于上述结论。`benchmark_refresh.py` 仍可单独创建样本；配对比较优先使用同一来源的 `compare_refresh.py`。

这些有效 PNG 均为 64×64 的相同生成小图；扫描比较关闭解码和分析。样本创建、首次建库不计入热刷新。它们不代表真实大原图解码、GPU 跑图耗时或任意磁盘吞吐。原始记录和中间失败日志保存在未提交的 `artifacts/`；可携带的汇总为 [1.8.0-sync.json](validation/1.8.0-sync.json)。

最终真实完成链路在独立 CPU ComfyUI、独立 input/output/data 中使用 LoadImage→SaveImage，不使用模型、不访问用户图源。普通 ComfyUI 网页关闭，通过无 `client_id` 的 API 连续提交 30 轮，开始时索引 14,399 项（输出 14,398、输入 1）。30 张新图全部入库、显示并解码，无手动刷新；服务端这段时间恰有 30 个成功刷新任务、0 个失败刷新。完成时间取宿主 `execution_success` 历史时间戳，显示取 DOM 新图片到达，解码取 `complete && naturalWidth > 0`。
